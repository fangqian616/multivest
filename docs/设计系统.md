# 设计系统：红 · 白 · 金

> 本文记录「智能多维投资系统」界面的设计立场与实现约束。
> 对应实现：`frontend/style.css`、`frontend/index.html`、`frontend/app.js`、
> `frontend/charts.js`、`tools/make_icon.py`。
>
> **本文档取代早期的「墨账」方案**（宣纸/印章/朱砂那一套）。
> 那套设计的问题不是不好看，而是**选错了受众**：它表达的是"这是一份庄重的文书"，
> 而这个产品的用户想看的是"今天市场发生了什么、我该动什么"。两者不匹配。

---

## 一、设计立场

三条不可让渡的规则：

### 1. 白底为主，界面不跟数据抢颜色

数据本身有颜色（涨红跌绿）。如果界面底色也有强烈倾向，整页会变成一堆互相
干扰的色块。所以：页面灰白（`#F5F6F8`）、卡片纯白（`#FFFFFF`）、
分隔只用 1px 浅灰线（`#E6E8EC`）。

### 2. 红只用于三件事

`#D92B2B` 是全系统唯一的主色，只出现在：
- **品牌**（顶栏一道 3px 渐变条、图标、主按钮）
- **上涨**（中国市场惯例，红涨绿跌）
- **关键结论**（研判结论、门禁失败、风险警报）

不在装饰上用红，红才有信息量。

### 3. 金色只用于「值得停下来看」的一处

`#C8A02E` 是次级强调色，用量必须极小：卡片顶端的一道金线、信心度条、
「首席研判官结论」卡片、关键分歧的裁决块。一屏之内金色出现超过三处，
它就失去了指路的作用。

## 三、字体

- **正文**：系统无衬线族（`PingFang SC` / `Microsoft YaHei UI`），13.5px / 行高 1.6
- **数字**：`Bahnschrift → Cascadia Mono → Consolas` 等宽栈，全程
  `font-variant-numeric: tabular-nums`

  这一条是这个设计里最关键的排版决定。金融看板上数字要竖向对齐才能比较，
  比例字体做不到。Bahnschrift 是 Windows 10 自带的 DIN 系技术字体，
  比等宽更紧凑、又比比例字体更整齐。

- **字号只有六档**：22 / 19 / 15 / 13.5 / 12 / 11 px。没有第七档。

## 四、信息密度

用户的原话是「可视化程度太低了」。密度不是靠缩小字号，而是靠**信息架构**：

| 手法 | 实现 |
|---|---|
| 一屏给结论 | 顶部 KPI 条 6 格：涨跌家数、上涨占比、平均涨跌、最强、最弱、利率代理 |
| 卡片带迷你走势 | 每个指数瓦片内嵌 60 日 sparkline + 昨收基准线，扫一眼知道位置 |
| 色块矩阵代替列表 | 22 个标的的涨跌做成热力网格，颜色深浅＝幅度，比表格快一个数量级 |
| 相关性可视化 | 22×22 热力图，红正蓝负，一眼看出哪些资产是真分散 |
| 多轴对齐 | 归一化到 100 的对比折线，把不同量级的标的放同一坐标系 |
| 分时 + K 线 | 当日分时（红绿分区）与 160 日日 K（含 MA5/20/60 + 成交量） |
| 图表全部内联 SVG | 无 CDN、无构建、离线可用；手机上也秒开 |

`frontend/charts.js` 提供 13 个图表函数（sparkline / intraday / candles /
lines / barRows / heatGrid / heatmap / radar / donut / gauge / drawdown /
waterfall / metricBar），全部返回 SVG 字符串、颜色走 CSS 变量、零依赖。

## 五、信息架构

```
顶栏：智能多维投资系统   行情总览 · 智能研判 · 家庭投资 · 决策记录 · 连接
```

| 一级 | 内容 |
|---|---|
| **行情总览** | KPI 条 → 核心指数瓦片（各带迷你走势）→ 分时图 → 大类表现 → 涨跌热力网格 → 涨跌排行 → 日K线 → 归一化对比 → 相关性矩阵 |
| **智能研判** | 六维雷达 + 评分条 → 研判官结论（建议仓位）→ 大类观点表 → 关键分歧 → 行动建议（带触发条件）→ 风险与观察清单 → 动量表 → 讨论时间线 → 历史研判 |
| **家庭投资** | 五个子页签：家庭档案 / 审议现场 / 配置方案 / 压力测试 / 分歧地图（即原「家和智投」全套家庭配置审议流程） |
| **决策记录** | 家庭审议与每日研判的留档列表 |
| **连接** | 二维码、PWA 安装、系统状态 |

**「每晚 AI 自动讨论」**落在「智能研判」：后端 `NightlyScheduler` 每交易日
20:30（`MULTIVEST_NIGHTLY_AT` 可配）自动跑一次，五维分析师并行研判 → 交叉辩论并
量化收敛 → 首席研判官产出看板 JSON，落盘 `daily/YYYY-MM-DD.json`。
也可以手动点「立即研判」并实时看进度流。

### 图表库令牌契约

`frontend/charts.js` 的函数签名里，颜色默认值写的是 `var(--red)` / `var(--green)` /
`var(--s1..--s8)` 这类名字。**这些名字必须同时存在于 `:root`**。

曾经漏过：`charts.js` 引用 28 个令牌，而 `style.css` 里缺 9 个
（`--green` 与 `--s1..--s8`）。缺令牌的后果很隐蔽 ——
**CSS 变量未定义时 `var()` 在计算值阶段失效，SVG 的 `fill` 会退化成黑色**，
阴线全黑、4 处未传 `colors` 的折线整条变黑。这类问题在灰度截图里不一定看得出来。

现在 `:root` 里已补齐，并注明：`--green` 与 `--down` 同值（charts.js 用西式命名，
设计系统用「红涨绿跌」语义命名），`--s1..--s8` 是图表多序列调色板。

### 用程序判定，而不是靠肉眼

`tools/shot/audit.mjs` 在真实页面上逐个检查 SVG 图元有没有渲染成黑色：

```bash
node tools/shot/audit.mjs
# ✅ board   SVG 22 个，图元 1264 个，黑色 0 个
# 合计：1458 个图元，0 个渲染成黑色
```

写这个脚本时踩过一个坑，值得记下来：**第一版审计报了 1381 个"黑色"，全是假阳性。**
因为 `<line>` 没有面积（`fill` 对它无意义）、`<g>`/`<title>`/`<defs>` 是容器与元数据，
它们的 computed `fill` 一律是默认黑，但屏幕上不会画出任何黑色。
必须按元素类型白名单 + 可见性（零尺寸 / opacity 0）过滤，
只统计**真的会绘制**的图元。**检查本身写错，比不检查更危险**——它会让你
去修一个不存在的问题。

## 七、怎么复核

```bash
python backend/app.py                       # 起服务
node tools/shot/shot.mjs --out docs/界面截图  # 截桌面 5 视图 + 手机 3 视图
```

改动视觉后用同一命令重截一遍即可肉眼比对。

> 注意：**不要用 `msedge --headless --screenshot`**。那条路在本机极不稳定，
> 同一命令时好时坏，失败时还没有任何错误输出。截图工具走 CDP（puppeteer-core）。
