# 家和智投 · 架构设计

## 一、设计目标与约束

| 目标 | 具体含义 | 架构上的体现 |
|---|---|---|
| **数字可信** | 家庭财务数字不能被模型编造 | 画像层全部确定性计算，作为事实文本注入提示词 |
| **共识可测量** | 不能"跑完轮数就算达成共识" | 移植 CV / Kendall's W / 三轨道终止 |
| **分歧不掩盖** | 收敛不了的问题必须显式裁决 | QC-9 强制校验裁决覆盖率 |
| **约束不越界** | 方案不得违反家庭承受力 | 10 项确定性硬门禁 + 兜底方案 |
| **结果可复现** | 同样的权重在同样的数据上给同样的账 | LLM 只出权重；工具、金额、压力测试全部确定性 |
| **离线可运行** | 不依赖可能被墙的外部接口 | 内置历史数据集；前端无 CDN、无构建 |
| **两端一体** | 手机与电脑不是两个独立 app | 单一后端 + 响应式同一套页面 + PWA |

关键架构决策：**LLM 负责判断，系统负责算术。**

## 三、数据流：从家庭输入到配置方案

### P0 家庭画像（确定性）

```
HouseholdInput ──▶ HouseholdProfile ──▶ to_prompt_text()
   资产/负债          总资产/负债率/应急月数      给分析师的紧凑事实文本
   现金流            生命周期/承受力评分
   目标/保障         权益上限/保障缺口
                     目标可行性
```

**风险承受力评分的五个维度**（客观能力，权重和为 1）：

| 维度 | 权重 | 评分逻辑 |
|---|---|---|
| 投资期限 | 20% | 距退休年数 / 30 |
| 收入稳定性 | 25% | (稳定性 − 1) / 4 |
| 杠杆水平 | 20% | `max(0, 100 − 负债率×250)` |
| 应急储备 | 20% | 覆盖月数 / 目标月数 |
| 供养负担 | 15% | `max(0, 100 − 供养人数×22)` |

**权益上限取两个约束的较小者**：
- 由风险评分线性映射：`10% + 评分/100 × 70%`
- 由可承受回撤反解：`可承受回撤 / 45%`（45% 是内置数据中权益类资产的真实历史最大回撤代理）

```python
equity_ceiling = min(eq_by_risk, eq_by_drawdown)
```

前者是"你想承受多少"，后者是"你能承受多少"，**取小者**。

### P1–P3 辩论与收敛

每位分析师在每一轮：
1. 看到**同一份**事实基础（画像 + 市场统计 + 压力情景定义）
2. 看到历轮全部发言
3. 输出本轮判断
4. **单独一次调用**只输出表态 JSON（Likert 1–5 分对每条主张）

> 为什么表态要单独一问：把表态块追加在长发言末尾时，长输出极易撞上 `max_tokens`
> 被截断，导致整块表态丢失、解析失败率飙升、进而触发解析失败率门使收敛信号失效。
> 单独一问输出短、稳。这是 consensus-pipeline 的实践经验。

每轮结束计算：
```
CV_overall        = mean(每条主张的 CV)，CV = pstdev(scores) / mean(scores)
Kendall_W         = 排序一致性（带并列秩校正，容忍部分缺失）
substantive_ratio = 非中立主张占比（拦截集体弃权式假收敛）
fail_rate         = 1 − 成功解析表态的分析师数 / 应到分析师数
```

然后 `check_termination()` 按 **守门 → 轨道1 → 轨道2b → 轨道2a** 的顺序判定。

### P5 方案接地（确定性）

LLM 只给**大类权重**（8 个键）。其余全部由系统计算：

```
大类权重 ──┬──▶ 类内等权展开到具体工具（来自数据集，可投的标的）
           ├──▶ 金额化（× 可投资资产）
           ├──▶ 历史回放（真实日收益加权，算年化/波动/最大回撤/年度收益）
           ├──▶ 前瞻测算（假设收益 + 真实相关矩阵，算 ΣΣ wᵢwⱼσᵢσⱼρᵢⱼ）
           ├──▶ 情景压力测试（真实历史窗口回放，折算成金额）
           ├──▶ 风险预算（边际风险贡献 MCTR = Σⱼ wⱼσⱼρᵢⱼ / σₚ）
           └──▶ 期限分层（短期 0-3 年 / 中期 3-10 年 / 长期 10 年以上）
```

### P8 质量门禁与兜底

```
方案 ──▶ run_qc() ──▶ passed?
                        ├─ 是 ──▶ 交付
                        └─ 否 ──▶ 带失败清单让委员会修订（1 次）
                                    ├─ 通过 ──▶ 交付
                                    └─ 仍不过 ──▶ conservative_weights() 兜底
                                                  按家庭约束确定性生成，并标注 fallback_used
```

兜底方案的生成规则（`portfolio.py::conservative_weights`）：
- 权益上限取家庭 `equity_ceiling` 的**一半**
- 现金+存款至少覆盖应急金目标
- 其余按债券 62% / 黄金 14% / 保险 9% 分配

### 表决（stance）
```json

```
- 键必须是**恰好**议题清单里的 ID，不得增删

## 五、实时推流协议（SSE）

`GET /api/stream/{run_id}` 输出 `text/event-stream`，每条 `data:` 是一个 JSON 事件。

| 事件类型 | 载荷要点 | 前端用途 |
|---|---|---|
| `phase` | `phase`, `label`, `detail` | 顶部步骤条高亮 |
| `profile` | 完整画像 | 渲染风险仪表与指标 |
| `market` | 资产目录、利率表、数据元信息 | 数据池载入提示 |
| `agent_start` | `agent`, `name`, `emoji` | 发言卡占位 + 打字光标 |
| `agent_done` | `agent`, `text` | 填充发言内容 |
| `arguments` | 议题清单 | 渲染立场矩阵表头 |
| `round_start` | `round` | 轮次分隔 |
| `stance_recorded` | `agent`, `stance` | 单元格逐个填色 |
| `convergence` | 完整 round_result | 收敛折线、终止提示 |
| `convergence_summary` | 全场收敛报告 | 分歧地图 |
| `draft` / `proposal_draft` / `proposal_final` | 草案与接地后的方案 | 方案页实时刷新 |
| `risk_verdict` | 通过 / 有条件通过 / 否决 | 风控结论条 |
| `qc` | 门禁报告 | 门禁清单 |
| `warning` / `error` | 文本 | Toast 提示 |
| `llm_call` | 调用元数据（含失败） | 控制台日志 |
| `done` | **完整结果对象** | 渲染全部页面 |
| `__end__` | 无 | 关闭连接 |

**断线重连**：事件在服务端保序落内存列表；前端重连时先补发全部历史事件。
心跳每 15 秒一次（`: keep-alive`），防止中间层断开长连接。

## 六、并发的处理

审议过程中大量调用是并行的：

| 阶段 | 并发模型 |
|---|---|
| P1 首轮发言 | `ThreadPoolExecutor(max_workers=5)`，5 位分析师同时调用 |
| P3 每轮发言 | 同上，5 位并行 |
| P3 表态采集 | 同上，5 位并行（每轮额外 5 次短调用） |
| P6/P7 | 串行（风控必须看到方案，委员会必须看到风控） |

共享状态（`Usage` 计数器、运行事件列表、订阅者列表）用 `threading.Lock` 保护。
`LLMClient` 本身是线程安全的。

## 七、为什么这样设计：三个具体取舍

### 1. 为什么让 LLM 只出权重，不让它算账？

因为**算术必须可复现**。如果让模型同时给权重和"预期年化收益"，两次运行的数字会不一致，
压力测试也会变成模型编的故事。现在模型给权重，系统用真实历史数据算它们的实际表现——
同样的权重永远得到同样的账。

### 2. 为什么需要"非中立守卫"？

CV = σ/μ。如果所有分析师对所有主张都打 3 分，σ = 0，CV = 0，"完美收敛"。
这是最危险的假信号——它看起来比真共识还漂亮。守卫检查平均表态是否落在中立带
（3±0.35）且非中立主张占比 < 50%，是则拒绝判定收敛并继续辩论。

### 3. 为什么兜底方案要按家庭约束生成，而不是报错退出？

因为**失败模式必须比成功模式更安全**。如果模型连续产出违反家庭权益上限的方案，
系统不能"报错让用户自己看着办"——那是把风险转移给最没有能力判断的人。
兜底方案用确定性的家庭约束生成，保证输出的下界是"不伤害这个家庭"。

## 八、可扩展点

| 想做什么 | 改哪里 |
|---|---|
| 换模型后端 | 界面设置窗口，或 `.env` 的 `DEEPSEEK_BASE_URL` / `DEEPSEEK_MODEL`（任何 OpenAI 兼容） |
| 加分析师 | `engine/agents.py` 的 `AGENTS` 列表加一条 `AgentSpec` |
| 改收敛阈值 | `engine/stance.py` 顶部的 `EPS1` / `EPS2` / `W_THRESHOLD` / `N_PLATEAU` |
| 改前瞻假设 | `engine/portfolio.py` 的 `FORWARD_ASSUMPTIONS`（每条都写了依据） |
| 加资产类别 | `engine/agents.py` 的 `ALLOC_CLASSES` + `tools/fetch_market_data.py` 的 `UNIVERSE` |
| 加压力情景 | `data/market.py` 的 `MARKET_SCENARIOS`（真实历史窗口） |
| 加门禁 | `engine/qc.py` 的 `run_qc()` 追加一个 `Check` |
| 换数据源 | `tools/fetch_market_data.py` 的 `fetch_kline()` |
